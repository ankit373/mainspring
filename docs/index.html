Local inference control plane

The mainspring that drives your local AI.

One stable OpenAI/Anthropic-compatible API in front. Pluggable engines — llama.cpp, MLX, Ollama, LM Studio, llamafile, GPT4All — behind it. Install and run only what a model needs. Build the control plane, not the kernels.

Quick start View on GitHub

Why

Local inference engines are commoditized and excellent — llama.cpp and Apple MLX are MIT-licensed and win on tokens/sec. What's missing is the control plane around them. The most-cited problems with the incumbents aren't kernel problems, they're control-plane problems:

  • Silent context truncation — prompts dropped with no error, differently per machine.
  • Silent CPU fallback — you think you're on the GPU; you aren't.
  • Zero authentication — tens of thousands of instances exposed publicly.
  • VRAM thrashing — evict-and-reload every call; leaks on model switch.
  • OpenAI-compat gaps — tool-call/streaming bugs break real SDKs.

What it does

One API, many engines

Per-model backend routing: serve a GGUF via llama.cpp, an MLX model, and an adopted Ollama model from one server.

Fail loud

/capabilities reports the real backend, device, GPU offload, and effective context — never silently smaller than asked.

VRAM-aware scheduling

Single-flight load, LRU + byte-budget eviction, KeepAlive idle-unload, optional preload at startup.

Standalone governance

API keys → named tenants with roles and per-tenant rate limits (429 + Retry-After) and token budgets.

Backpressure

Per-model in-flight limit + bounded queue. Returns 503 instead of letting latency collapse.

Observability

Prometheus /metrics (TTFT, tokens/sec, residency, inflight/queued) + a JSONL usage ledger.

Verified install

Opt-in only. SHA-256-pinned artifacts, optional ed25519 signed manifests. Never installs silently.

Deploy anywhere

Single static binary, distroless image, Helm chart (HPA, ServiceMonitor, GPU nodes). Graceful drain via /readyz.

Quick start

# build
go build -o mainspring ./cmd/mainspring

# see which engines are present (detect-first)
./mainspring backends

# diagnose your environment
./mainspring doctor

# serve a local GGUF over the OpenAI API
./mainspring serve --model qwen2.5-coder=/path/to/model.gguf --addr :11500

# talk to it with any OpenAI client
curl localhost:11500/v1/chat/completions -H 'content-type: application/json' -d '{
  "model": "qwen2.5-coder",
  "messages": [{"role":"user","content":"hello"}]
}'

# the fail-loud truth about what actually ran it
curl localhost:11500/capabilities

API & CLI

Endpoints

  • POST /v1/chat/completions
  • POST /v1/completions
  • POST /v1/embeddings
  • POST /v1/messages — Anthropic (streaming translated)
  • GET /v1/models
  • GET /capabilities — fail-loud device/offload/ctx
  • GET /metrics — Prometheus
  • GET /healthz · GET /readyz

Commands

  • mainspring serve
  • mainspring backends
  • mainspring models
  • mainspring install <backend>
  • mainspring doctor
  • mainspring version
Relationship to Hydra. Mainspring is an inference head; Hydra is a provider-neutral router/trust control plane above it. They meet over the standard OpenAI-compatible boundary. Hydra works with everything (Ollama, OpenAI, Anthropic, any OpenAI-compatible endpoint) and never depends on Mainspring — Mainspring is simply the head it integrates with best.
