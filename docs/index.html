The mainspring that drives your local AI.

One stable OpenAI- and Anthropic-compatible API in front. Six pluggable engines behind it. Mainspring is the layer around inference — fail-loud correctness, VRAM-aware scheduling, and its own governance. It never writes a kernel; it wraps the ones that already win.

Where we exist

Models got small enough to own.

When there was one frontier model behind one API key, there was nothing to manage. What changed is that open weights and small models got good enough to run yourself — so now you have many models and a fixed amount of metal. Notice that the problem gets harder as the models get smaller.

A dozen small models on one GPU is a scheduling and governance problem, not a modelling one. Models got small enough to own — nothing got built to run them like you own them.

Which layer

A control plane, not another runner.

Mainspring is one rung of the local stack. It doesn't compute tokens and it doesn't route across vendors — it makes a single local head honest and governable, so whatever sits above it can trust what it says.

Your app agents, editors, anything already written against the OpenAI or Anthropic SDK
Trust control planeacross heads Hydra — decide which head should answer, to a target confidence of correctness, at what cost, with an accountability trail. Simpler proxies live at this tier too (LiteLLM, OpenRouter), but they forward traffic rather than reason about whether the answer is right.
Inference control planeone head Mainspring — make one head honest and governable: keys and quotas, VRAM residency, guardrails, fail-loud truth, spend. Whatever decides which head to use is only as good as what each head reports about itself.
Runner Ollama · LM Studio · llamafile · GPT4All — package a model and serve it. Mainspring adopts these as backends rather than replacing them.
Engine llama.cpp · MLX — the actual compute. MIT-licensed, already excellent. Mainspring never writes a kernel.

So it composes rather than competes. If Ollama is already running, Mainspring detects and adopts it — your models keep working, and they gain authentication, quotas, residency budgeting and a fail-loud contract they didn't have.

Two control planes, different questions. Hydra asks which head should answer this, and how confident are we that it's right. Mainspring answers what is true about this head right now. Hydra is provider-neutral, works with any OpenAI-compatible endpoint, and never depends on Mainspring — and Mainspring is equally designed to be useful with nothing above it at all. They compose well precisely because neither assumes the other.

The gap

The engines are solved. The control plane isn't.

llama.cpp and Apple MLX are MIT-licensed and win on tokens per second. Writing another kernel is not the opportunity. The problems people actually hit with local inference are control-plane problems — and every one of them is a correctness problem wearing a convenience costume.

  • Silent context truncationYour prompt is quietly dropped to fit, differently on each machine. No error, no header, no way to know.
  • Silent CPU fallbackYou believe you're on the GPU. You are not. Throughput says so; nothing else does.
  • Zero authenticationTens of thousands of local inference servers sit exposed with no key, no quota, no audit trail.
  • VRAM thrashingEvict-and-reload on every call; a long generation gets its own runner killed out from under it mid-stream.
  • OpenAI-compat gapsTool-call and streaming edge cases break real SDKs — the ones your code is already written against.
  • No spend signalLocal is "free" until you're choosing between a local head and a paid one and have no number to compare.
Fail loud

Same request. Same body. One of them tells you what happened.

This is a real degraded case: you asked for GPU offload and the engine quietly loaded on CPU. Nothing about the response body changes — which is precisely why it goes unnoticed for weeks.

Straight to the engine
HTTP/1.1 200 OK
content-type: application/json

{"choices":[{"message":{"role":"assistant",
  "content":"..."}}],
 "usage":{"prompt_tokens":9014,
          "completion_tokens":218}}
  • Did that run on the GPU, or fall back to CPU
  • Did my 9,000-token prompt fit, or get truncated
  • And if it degraded — would I ever find out
Through Mainspring
HTTP/1.1 200 OK
content-type: application/json
X-Mainspring-Backend: llamacpp
X-Mainspring-Device: cpu
X-Mainspring-Warning: GPU offload requested but
  engine loaded on CPU (silent fallback)
X-Mainspring-Context-Warning: prompt (9014 tokens)
  + max_tokens 512 exceeds model context
  window of 8192 tokens

{"choices":[{"message":{"role":"assistant",
  "content":"..."}}],
 "usage":{"prompt_tokens":9014,
          "completion_tokens":218}}
The body is byte-for-byte what the engine returned — token counts included. The difference is that the two failures are now impossible to miss. Backend, Device and Warning ride on every response, not behind a debug flag. The context header appears once you've told Mainspring the model's window (ctx).
What it does

Fail loud. Schedule honestly. Govern itself.

Everything below ships today in v0.2.0 — verified against the binary, not a roadmap.

One API, many engines

Two dialects, one server

OpenAI (/v1/chat/completions, /v1/completions, /v1/embeddings, /v1/models) and Anthropic /v1/messages — tool use, images and streaming all translated.

Same rules on both dialects

Auth, per-tenant budgets, the context guardrail, clamp, the concurrency gate, timeouts, the breaker and cost accounting govern /v1/messages exactly as they govern the OpenAI paths. The response cache, coalescing, retry and model fallback are OpenAI-path only today.

Per-model backend routing

One server can serve a GGUF on llama.cpp, an MLX model, and an adopted Ollama model at the same time. Friendly aliases resolve on every path.

Two kinds of fallback

Backend-level (same model, another engine) and model-level (model_fallbacks — a different model answers). Only ever before the first byte reaches the client.

Model auto-discovery

Opt-in: enumerate what your adopted engines already hold and expose it automatically. Configured models win an id clash.

Fail loud, never silently degrade

The truth, in headers

X-Mainspring-Backend, -Device and -Warning on every response; /capabilities reports real GPU offload and effective context.

Degraded means degraded

A shrunk context or a silent CPU fallback is degraded. A model you deliberately configured CPU-only (gpu_layers: -1) is not — intent is not a fault.

Context guardrail

Opt-in enforce_context rejects a request that cannot fit instead of letting the engine truncate it. Per-model override downgrades to a warning header.

Exact token counting

/v1/tokenize returns {tokens, exact} — the model's real count when it's resident on a tokenizing engine, honestly flagged as an estimate when not. input takes a string or an array of strings; anything else is a 400, never a silent zero.

Graceful clamp

Rather than rejecting an over-budget max_tokens, opt in to shrink it to the room actually left and report the change on X-Mainspring-Clamped.

Embeddings counted too

The guardrail, clamp and precise counting all read an embeddings input field — not just messages. A large embeddings call trips the guardrail instead of measuring as zero.

No fabricated endings

An upstream error is an error — a backend 500 becomes 502 upstream_error, never an empty success. A generation cut mid-stream ends with a terminal error event on both dialects, not a stop reason it didn't earn, and the breaker is told it failed even though the stream already went out at 200. A truncated non-streaming body is never cached and never handed to coalescing followers.

Your Ctrl-C is not an outage

A caller that cancels its own request is not a backend failure, so client disconnects can't open the circuit for every tenant — and a caller cancelled while queued gets no misleading 503 written to a connection that's already gone. A real timeout still counts.

Residency & reliability

Eviction never breaks a request

Single-flight load, LRU and byte-budget eviction, KeepAlive idle-unload — and none of them pull a runner out from under an in-flight generation, even one that outlasts its own KeepAlive.

Circuit breaker + health probe

After N consecutive failures a model fast-fails with 503 instead of paying the timeout, until a cooldown elapses and a half-open probe succeeds. A background prober can recover it without live traffic.

Backpressure, not collapse

Per-model in-flight limit and a bounded queue return 503 with Retry-After rather than letting latency melt down.

Retry & coalescing

Transient upstream failures retry with backoff, always decided before the first byte so streaming stays safe. Identical requests that pin an explicit temperature: 0 and are in flight together collapse to one backend call — the same bar the response cache uses, because sharing one sample is only honest when the caller asked for a deterministic one. A replay carries the payload's headers, never the leader's request id or quota headroom.

Governance & observability

Standalone governance

API keys map to named tenants with roles, rate limits and token budgets. Quota headroom rides on X-Mainspring-RateLimit-* and -TokenBudget-* so clients back off before they're refused.

Real cost accounting

Optional per-model USD rates turn real token usage into spend — in the ledger, in mainspring_cost_usd_total, and per-model in /v1/quality. Priced only from exact usage, never guessed.

Percentiles, not just means

mainspring_{duration,ttft,queue_wait}_ms_{p50,p90,p99}. Queue wait is measured separately from generation time, so backpressure latency is distinguishable from real work.

Traceable by default

X-Request-ID, W3C traceparent propagation, an append-only JSONL usage ledger and an optional access log that names the tenant on every authenticated line — no OTel SDK dependency.

Operable at runtime

SIGHUP hot-reload and an admin API: drain, reload, load/unload a model, reset a breaker, clear the cache, read effective config and per-tenant usage. Admin-gated, and each action is attributed to its tenant in the access log.

Deploy anywhere

One static binary, a distroless image, and a Helm chart with HPA, ServiceMonitor and GPU-node scheduling. TLS and graceful drain included.

A mechanism, close up

Failing fast is easy. Recovering honestly is the hard part.

When a backend starts failing, refusing traffic is the simple half. The interesting half is deciding when to trust it again — and telling your dashboards the difference between "still broken" and "cautiously trying".

healthy — traffic flows
N failures→
Open
fast-fail 503 — no timeout paid
cooldown→
Half-open
exactly one probe allowed through


    
Why two gauges. A single "tripped" metric collapses open
      and half-open into the same number, so an operator watching Prometheus cannot tell a
      backend that is still dead from one that is actively being retried. Mainspring keeps
      mainspring_breaker_open as-is for existing dashboards and adds a separate
      half-open gauge — so recovery is observable, not inferred. A probe that fails sends it straight
      back to open and restarts the cooldown; a probe that succeeds closes it.

  






  Quick start
  
Detect first. Install nothing you didn't ask for.

  
Mainspring looks at what your machine already has before it proposes anything. Managed
    engines can be installed on demand — opt-in and checksum-verified. Adopted engines are never
    installed at all.


# build
go build -o mainspring ./cmd/mainspring

# which engines are already on this host?
./mainspring backends

# full environment diagnosis — backends, config, models, ports
./mainspring doctor

# serve a local GGUF over the OpenAI API
./mainspring serve --model qwen2.5-coder=/path/to/model.gguf --addr :11500

# talk to it with any OpenAI client, unchanged
curl localhost:11500/v1/chat/completions -H 'content-type: application/json' -d '{
  "model": "qwen2.5-coder",
  "messages": [{"role":"user","content":"hello"}]
}'

# and ask what actually ran it
curl localhost:11500/capabilities
→ backend=llamacpp  device=gpu  gpu_offload=true  effective_ctx=8192

    Where Hydra fits. Mainspring is an inference head;
    Hydra is a provider-neutral trust control
    plane that routes across many heads to a target confidence of correctness. They meet over the
    standard OpenAI-compatible boundary. Hydra works with everything — Ollama, OpenAI, Anthropic, any
    compatible endpoint — and never depends on Mainspring. Mainspring is simply the head it
    integrates with best, because it is the one that reports honestly on itself; and it is designed
    to be useful deployed entirely alone.
